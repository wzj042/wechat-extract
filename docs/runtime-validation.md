## 本轮发现：需要明确 DAT 长度模式

这批样本的 DAT 头部 `aes_size` 均为 1024，但其语义是填充前明文长度；AES 密文段需要按 `plaintext` 模式处理，包括额外的填充块。默认 `ciphertext` 将边界放错后，仍可能恢复出 PNG/JPEG 文件头，甚至有 JPEG 能完整加载，不能据此认定模式正确。

本机此次样本应在工作流中的图片导出命令后增加：

```powershell
--aes-size-mode plaintext
```

这只是完整命令的附加参数，不能单独执行。MCP 对应配置项为 `"aes_size_mode": "plaintext"`，批量图片入口也支持同名参数。本轮只在独立验证命令中指定，未改生产配置或全局默认值。

既有验证中也存在 `ciphertext` 模式的有效样本，见 [历史媒体验证](media-validation.md)。不能把本轮结论推广为所有微信版本和所有 DAT 都应使用 `plaintext`。当时的版本由调用方显式选择；现行默认值见上方复测记录。

## 验证边界

本轮验证了数据库取密钥、解密、消息读取及普通 PNG/JPEG 图片导出。没有实测 WXGF/HEVC 转码、语音、视频、文件、表情下载、MCP 协议或持续 `watch`。SQLite 检查和有限消息抽样不代表账号全量消息语义校验，也不证明未同步到本机的历史数据可读取。
